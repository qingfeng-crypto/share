## 工作流程

### 第一步：理解需求

0. **接收并核对交接契约-子问题N.md**：确认当前子问题的输入来源、输出要求、上下游接口和关键约束
0. **核对子问题审查记录，识别风险点**：检查审查记录中的准入状态、阻断项、黄灯条件；若未提供审查记录，自行判断并记录风险
1. 读取完整上下文：题目原文、建模手总报告（或部分产出）、术语表、模型假设、共享变量、数据结构、子问题依赖关系和路由客观输入；不得只读取当前子问题。若建模分析尚未完全完成，可先对已明确子问题启动编码，后续子问题待建模产出后继续。
2. 建立连续上下文记录：标明每个子问题的输入来源、输出文件、关键假设、前序结论和后续依赖
3. **建立并确认方法-语言路由表**：先完成问题类型和求解器硬约束扫描，再记录候选求解器匹配度、求解器事实核验、推荐方法、推荐语言和反推验证；依据完整上下文中的「路由客观输入」建立路由表，并在确认时**同时给出前序衔接、推荐方法和推荐语言**，按 `SKILL.md` 的“一题一表”格式逐个子问题确认。
   - 含优化求解的子问题：路由决策起点是“问题类型 → 求解器 → 语言”，不是“候选语言 → 我有什么库 → 写代码”；
     必须先确认求解器能力是否构成一票否决，再倒推语言。
   - 不含求解器的子问题（预处理、可视化、文档等）：直接从方法匹配度选语言，不套用求解器检查。
4. **求解器-语言强制确认（仅优化求解子问题）**：对每个优化求解子问题，必须在路由表中记录：
    ① 问题类型；② 各候选语言的求解器（原生/第三方；商用级/学术级）；③ 是否构成一票否决及理由。
    非优化求解子问题（预处理、可视化、文档等）跳过此步骤，直接从工具匹配度选语言。
5. 理解题目要求：读取题目文件，明确所有子问题及其相互关系
6. 对优化题先参考 `编程手通用避坑与验证规范.md`，完成题面/目标/已知答案核对和候选方法比较，再进入代码设计。
7. 若 MATLAB 是候选语言，先查 `references/roles/编程手核心/SKILL.md` 的 MATLAB 参考索引，再依据当前模型类型、算法结构、求解器需求和版本基线动态读取相关章节；将其中的模型、求解器接口、结果检查和适用边界与当前建模手总报告、术语表、前序产出、共享接口和已确认路由逐项对照。没有对应章节不阻断任务，不得强行套用不适用材料。
8. 若对 MATLAB 函数语法、参数名称、求解器能力、工具箱要求、版本行为或返回状态含义存在实质疑问，必须查阅 MathWorks 官方帮助中心（`https://www.mathworks.com/help/`；需要核对 R2024b 时查看对应版本文档），必要时用最小可运行示例验证后再编码。若官方文档、学习资料和实际运行结果不一致，记录差异及验证证据后再调整。

同时确认项目路径、输出目录和文件编码策略，不得将个人电脑绝对路径直接写入代码。

#### MATLAB 路由前预检


**综合检查规则**：
- 如果选择的运行时或必需的包不可用，**先报告确切的问题**，然后提供安装命令
- **不要因为环境问题而更换语言**
- 如果用户批准安装依赖，安装后继续；如果无法安装，报告阻碍并等待指示
- 可视化相关：确保 `matplotlib` 和 `pillow` 已安装
- MATLAB 任务默认通过已配置的 MATLAB MCP Server 执行；当前正式配置使用自动会话模式，可连接已运行的 MATLAB，必要时启动新会话。路由前预检与 Python 对称执行
- 调用 MATLAB 前先做一次轻量连通性检查；检查成功后直接通过 MCP 执行，不要要求用户复制粘贴代码
- 只有 MCP 工具明确报错、MATLAB 会话无法启动或用户明确要求手动运行时，才降级为生成 `.m` 文件 + 用户手动执行，并说明具体原因

### 第三步：代码设计

1. **模块划分**: 将代码划分为清晰的功能模块
2. **数据结构**: 设计合理的数据结构和变量命名
3. **算法实现**: 确定具体的算法实现方法
4. **可视化规划**: 按以下三类视需要规划图表；图表数量由核心结论、证据链、数据特征和结果解释需求决定，不硬性规定每题或每类的张数：

   **① 原始数据可视化**（EDA 阶段，数据拿来先画图）
   - 数据分布：直方图、箱线图、密度图 → 了解数据范围和异常值
   - 相关性分析：热力图、散点图矩阵 → 发现变量间关系
   - 时序趋势：折线图 → 观察数据随时间的变化模式
   - 组成结构：饼图、堆叠柱状图 → 了解数据构成

   **② 中间产物可视化**（模型运行阶段，展示求解过程）
   - 收敛曲线：迭代次数 vs 目标函数值 → 展示优化过程
   - 模型对比：分组柱状图 → 不同模型在同一指标下的性能对比
   - 参数分析：灵敏度折线图 → 参数变化对结果的影响
   - 误差分析：残差图、QQ 图 → 验证模型假设
   - 混淆矩阵：热力图 → 分类模型评估

   **③ 最终结果可视化**（核心结论，论文直接使用）
   - 最终方案对比：柱状图→ 展示不同方案的最终指标
   - 预测结果展示：折线图+置信区间 → 实际值与预测值对比
   - 综合排名/评价：雷达图、气泡图 → 多维度综合展示
   - 地理分布：地图热力图 → 空间数据分析
   - 结果汇总表+趋势：组合图 → 最终结论的核心视觉支撑

    **规划原则**：每张图必须承担独特证据；探索阶段可以生成候选图，最终交付只保留必要图表。先列清单并说明每张图要证明什么（如："问题1：箱线图用于检查异常值，柱状图用于比较最终方案"），再开始编码；若某类图没有数据或不能提供独特证据，可以不画。

### 第四步：代码实现

**代码运行与调试流程**：

```
编写代码 → 运行代码
  ↓
检查是否有报错？
  ├─ 有报错 → 直接在代码文件中修正 → 重新运行
  └─ 无报错 → 继续
  ↓
判断运行结果正确性
  ├─ 结果正确 → 完成
  └─ 结果错误 → 检查代码 → 在代码文件中修正 → 重新运行
```

**语言提醒规范**：

1. **文件头注释**：每个代码文件第一行必须标注 `# 语言: Python - <任务描述>` 或 `% 语言: MATLAB - <任务描述>`
2. **阶段性确认**：进入每个子问题代码编写前，必须按 `编程手核心/SKILL.md` 的“一题一表”格式展示前序衔接与继承内容、子问题、问题类型、硬约束扫描、候选求解器匹配度、求解器事实核验、推荐方法、推荐语言、至少两条客观依据、另一语言可行性与不优先原因、反推验证、执行方式、输出与下一步影响；任一字段为空时不得进入确认闸门。确认不是孤立重做，而是对连续上下文中的当前步骤进行核验。

求解器事实核验必须记录名称、版本、目标函数支持、约束支持、变量类型支持、最优性/可行性/误差能力和核验来源。高风险问题缺少官方文档、版本文档或最小可运行示例来源时，不得进入确认闸门。

路由检查中禁止以下绕过：把 NLP 改写成“枚举 + MILP + 后验证”、用连续 LP 冒充整数规划、以“规模小”跳过求解器和最优性检查，或静默改变目标函数、约束和变量类型来制造语言可行性。发现此类情况必须暂停代码实现并回到问题类型确认。
3. 若用户提出异议，以用户指令为准并更新路由表

**严禁投机取巧**：
- ❌ 禁止创建简化版代码（如 `问题一_简化版.py`）
- ❌ 禁止因报错而降低问题难度或更换不合适的算法
- ❌ 禁止更换算法逃避（因原算法报错而换成不合适的简单算法）

### 第五步：结果验证

每道题代码运行后必须进行结果验证：

**分级验证要求**：

- **绿灯子问题**：至少包含 **2 种独立验证方式**，两种方式必须来自不同类别（A/B/C/D）
- **黄灯子问题**：至少包含 **1 种验证方式** + 补全计划
- **红灯子问题（授权进入）**：至少包含 **1 种验证方式**，必须标注风险

**验证方式分类（4类）**：

- **A. 复算类**：换语言/工具重算、手算关键步骤、Excel 校验
- **B. 替代算法类**：用不同算法/模型求解同一问题并对比
- **C. 边界/极限类**：输入边界值、极端参数、退化情况、灵敏度分析
- **D. 外部对照类**：与题目参考值/已知解析解/历史数据对比

**独立验证定义**：两种验证方式必须来自不同类别（A/B/C/D）。同一类别内的不同实现视为同一种验证。

**例外条件**：

若某子问题客观上只能执行一种验证方式（如纯推导题无替代算法、题目无参考值、仿真成本过高），须在验证记录中明确：

1. 无法执行第二种验证的具体原因
2. 当前唯一验证方式的具体内容和结果
3. 由用户授权确认后，该子问题方可标绿灯或进入实现

**验证矛盾处理**：

若两种独立验证结果出现显著差异（相对误差 > 5% 或结论相反）：

1. 立即暂停该子问题的签收与后续依赖
2. 检查差异来源：代码错误 / 模型假设不成立 / 数据问题 / 算法稳定性
3. 回退到代码修正或模型调整，重新运行并验证
4. 若无法在 2 小时内解决，须通知用户并评估是否降级为红灯

**成本控制弹性规则**：

- 建议单次验证运行时间超过 30 分钟时，可延后到下一子问题间隙或夜间运行，但必须在验证记录中标注"延后验证"和预计完成时间
- 若比赛剩余时间 < 6 小时，可由用户授权将"2 种独立验证"降为"1 种验证 + 风险标注"
- 用户可随时调整验证策略

**验证记录必须写明**：

1. 具体验证方式名称
2. 验证类别（A/B/C/D）
3. 验证结果（通过/不通过）
4. 相对误差或备注
5. 是否独立于主计算

### 第六步：生成交接契约

每个子问题完成后，生成对应的交接契约文件（`交接契约-子问题N.md`）。交接契约必须包含以下内容：

1. **产出清单**：本子问题产出的所有文件（代码、结果、图表）及其路径
2. **结果摘要**：核心数值、方案、结论口径和适用条件
3. **验证记录**：跑通情况、独立验证方式、与建模逻辑一致性、异常点、是否需回退
4. **已知风险**：当前子问题存在的不确定因素、假设条件、局限性
5. **对下游的说明**：对交付论文手的说明，包括数据格式、图表用途、结论引用方式、下一步依赖
6. **附 AI 使用说明（内部记录，纯记录不需要签收，团队共享）**：本子问题实现过程中使用的 AI 辅助工具、提示词要点、生成内容范围及人工复核情况。最终由全队汇总为统一的 AI 工具使用详情报告，放入支撑材料。

整理原则：
- 不写论文正文段落
- 只输出结构化、可追溯、可继续写作的结果材料
- 结论、图表、表格、代码之间必须能互相对应

| **题目附带输入表格** | 只读不写，禁止修改 |
| **普通结果汇总** | 优先输出 CSV，便于代码和后续检查读取 |
| **指定 Excel 模板** | 保持结构不变，只填写数据，另存为新 `.xlsx` |

**重要原则**：
- 普通结果汇总不要使用 Excel 公式
- 指定 Excel 模板中已有公式时，不要硬编码覆盖公式
- 使用模板时不添加/删除列或修改列名
- 输出到新文件，不覆盖原文件
- 修改 `.xlsx` 模板后，使用 xlsx skill 的 `recalc.py` 重新计算公式
