# 编程手通用避坑与验证规范

本规范沉淀实际求解过程中具有迁移性的工程与算法教训。它服务于"先核对、再选法、后编码、独立验证"的主线，不替代具体题目的建模分析，也不把某一种算法固定为默认答案。

## 前置原则：求解器优先于语言

> **优化求解阶段，选语言之前先选求解器。** 这是路由决策的强制检查项，不可颠倒。

### 正确的决策链

```
问题类型 → 求解器能力矩阵 → 倒推语言
```

### 错误的决策链

```
候选语言 → 我能用它的什么库 → 写代码
```

### 三个强制检查问题

在优化求解阶段建立路由表之前，必须回答以下三个问题，缺一不可：

1. **这是什么问题类型？**
   连续 LP / 整数规划（IP）/ 混合整数线性规划（MILP）/ 二次规划 / 非线性规划 / 微分方程 / 蒙特卡洛仿真 / ……

2. **各候选语言在这个类型上有什么求解器？**
   - 原生内置的？还是第三方的？
   - 商用级（工业验证）还是学术级（研究原型）？
   - 调用方式：一行 API 还是需要手动实现整个算法框架？

3. **类型匹配度是否构成一票否决？**
   如果问题类型在两种语言上的求解器能力存在质的差距，不存在"两者都可以"的平局——差距大的那一方直接出局，不需要继续比较。

### 实践案例：整数规划的选型教训

**场景**：求解 `max z = x₁ + x₂` 的整数规划问题，约束含分数系数，最终答案 `x₁=3, x₂=1, z=4`。

**错误选型**：Python + scipy。scipy 只有 `linprog`（连续 LP 求解器），没有内置整数规划求解器。结果被迫手动编写循环调 LP 模拟分枝定界，效率低且容易出错。

**正确选型**：MATLAB + `intlinprog`。`intlinprog` 是内置商用级 branch-and-cut 求解器，底层 C/C++ 编译，支持 presolve、割平面、启发式搜索，一行调用直接出最优解。

**错误决策链**："Python 方便我手动编码分枝定界（教学演示思维）" → 忽视了求解器能力差距。

**正确决策链**："整数规划 → 需要 MILP 求解器 → Python scipy 无内置整数规划求解器 → MATLAB `intlinprog` 一票通过"。

### 一句话总结

> 优化求解选型：不要问"用什么语言写代码"，先问"这个子问题用什么求解器解"。求解器能力决定语言，不是反过来。

## 一、先核对题面、代码和已知答案

正式求解前，必须确认题面、代码实现和已知答案描述的是同一个模型：

1. 将目标函数独立实现为可测试函数；
2. 将已知候选解代入目标函数，重新计算目标值；
3. 逐条检查候选解是否满足约束、变量边界和整数性；
4. 核对变量顺序、系数符号、约束方向和单位；
5. 若题面结果与独立计算不一致，先暂停算法开发，定位模型或数据差异。

最小核对链条：

```text
题面公式 → 独立目标函数 → 代入已知解 → 检查约束 → 再比较算法
```

不能因为题目附带“标准答案”就跳过独立核算。答案、题面和代码只要有一处不一致，后续性能比较和正确性结论都不可靠。

## 二、优化题先做方法对比，再编码

拿到优化题时，先建立简短的方法对比，再选择实现方案。至少比较：

| 方法类型 | 是否通常保证全局最优 | 适用场景 | 主要风险 |
|---|---|---|---|
| 全量枚举/剪枝枚举 | 可以，但取决于枚举完整性和剪枝安全性 | 变量少、范围小、约束能显著收缩 | 搜索空间爆炸、剪枝错误 |
| 分支定界 | 可以，但要求上下界正确 | 有可靠松弛或乐观上界的整数优化 | 上界不安全会误剪，安全上界过松会很慢 |
| 求解器精确方法 | 视模型类别和求解器能力而定 | 可写成 LP/MILP/QP 等标准形式 | API、模型类别或求解器能力判断错误 |
| 启发式/局部搜索 | 通常不能证明全局最优 | 大规模、需要快速高质量方案 | 结果依赖起点和参数，可能漏掉更优解 |
| 蒙特卡洛/随机采样 | 不能作为一般整数优化的最优性证明 | 概率估计、积分、风险和情景模拟 | 高维约束下命中高质量区域概率低 |

方法选择必须结合变量规模、约束结构、是否要求证明最优、可接受运行时间和后续验证方式。不能拿到题目就直接写枚举，也不能把随机方法的最好样本称为全局最优。

## 三、精确算法必须证明上界安全

对最大化问题，分支定界或剪枝枚举必须区分：

- **下界**：当前已知可行解的目标值；
- **上界**：某节点理论上可能达到的最大目标值；
- **安全剪枝**：只有当节点上界不超过当前下界时，才能删除该节点。

必须满足：

\[
UB(\text{node})\geq \text{该节点真实最优值}.
\]

如果计算出的“上界”低于已经找到的可行解，说明模型、符号、变量顺序、约束或上界推导至少有一处错误，不能解释为“松弛太松”，也不能继续使用该上界剪枝。

精确算法交付时应报告：

1. 当前最好可行解及其目标值；
2. 全局上界；
3. 最优性间隙或证明已经闭合；
4. 剪枝规则及其安全性依据。

## 四、区分求解方法、近似方法、随机模拟和验证程序

代码输出的性质必须与方法能力一致：

| 类别 | 主要职责 | 能否直接声称全局最优 |
|---|---|---:|
| 精确优化 | 求解并在条件满足时证明最优 | 通常可以 |
| 启发式/局部搜索 | 快速寻找高质量可行解 | 不可以，除非另有证明 |
| 随机模拟/蒙特卡洛 | 估计概率、风险、积分或情景分布 | 不可以 |
| 验证程序 | 检查目标、约束、边界和独立结果 | 不一定，它主要提供证据 |

推荐组合：

```text
启发式/贪心 → 找到高质量可行解（下界）
精确算法 → 证明最优或缩小最优性间隙
蒙特卡洛 → 评估随机扰动下的方案表现
独立检查 → 核对目标值和约束满足情况
```

## 五、求解与验证尽量使用不同逻辑

验证不是把同一个函数无修改地再运行一次。至少应分层：

### 1. 局部验证

- 独立计算目标函数；
- 独立计算每条约束残差；
- 检查变量边界、整数性和非负性；
- 检查输出文件和关键中间量。

### 2. 结构验证

- 复用已经证明的变量上界和约束收缩；
- 检查剪枝前后的可行域是否一致；
- 检查目标值、约束矩阵和变量排列是否同步；
- 对小规模实例用全量枚举建立基准。

### 3. 独立交叉验证

尽量使用不同逻辑、不同实现或不同求解器复核：

- 分支定界结果用独立约束检查；
- 求解器结果用目标函数重算；
- 正式规模结果用小规模全枚举验证算法逻辑；
- 需要时用第二种求解器或独立实现比较目标值。

验证程序必须尽量独立于求解程序，否则可能只是重复同一个错误。

## 六、路径必须可移植

禁止把个人电脑路径写死在代码中，例如：

```python
"/c/Users/example/mip_project/results/"
```

Python 推荐以脚本或项目目录为基准：

```python
from pathlib import Path

PROJECT_ROOT = Path(__file__).resolve().parent
RESULTS_DIR = PROJECT_ROOT / "results"
FIGURES_DIR = PROJECT_ROOT / "figures"
RESULTS_DIR.mkdir(exist_ok=True)
FIGURES_DIR.mkdir(exist_ok=True)
```

MATLAB 使用 `fullfile` 和明确的项目目录，不依赖个人机器的绝对路径。输出目录、输入文件和中间结果的路径应在 README 或配置区域中说明。

## 七、陌生求解器 API 先做最小验证

不熟悉的求解器或建模库，必须先用最小例验证 API，再嵌入完整模型：

1. 验证变量创建和边界设置；
2. 验证目标表达式支持的运算类型；
3. 验证约束方向和整数变量声明；
4. 验证求解器类别是否支持当前模型（LP、MILP、QP、MINLP 等）；
5. 验证状态码、目标值和变量值的含义。

特别注意：不要假设建模库支持变量幂、变量自乘或任意非线性表达式。遇到二次目标或非线性约束时，应先查官方文档，确认使用合适的 QP/MINLP 工具，或明确采用线性化、分段近似等替代模型。

最小验证示例应尽量只包含一个变量、一个目标和一个约束，确认接口后再扩展。

### 第七节·补充：MATLAB 工具箱函数三层预检规则

对 MATLAB Control System Toolbox 等以**对象方法**形式注册的函数，`exist(name)==0` **不等于不可用**。
必须执行以下三层判断，三层均通过才记为“可用”：

| 层级 | 命令 | 通过标准 |
|---|---|---|
| 第 1 层 | `exist(name)` | ≥1（顶层函数存在） |
| 第 1.5 层 | `which(name, '-all')` | 有路径返回（含 `@ClassName/method.m` 格式的类方法路径） |
| 第 2 层 | `exist(name) == 0` 时 | 检查路径是否指向 `@ClassName/` 目录 |
| 第 3 层 | 最小可运行调用 | 创建最小对象（如 `sys=tf([1],[1 1])`）并实测 `method(sys)` 调用不报错 |

三层中有任意一层失败，才记为“不可用”；**不可跳过第 3 层而仅凭第 1 层结论**。
Control Toolbox 中 `bodeplot` / `stepplot` / `pzplot` / `pidtune` 均属于此类对象方法，
`exist()` 返回 0 属正常现象，不得因此标记为缺失。

**真实教训（已发生）**：曾用 `which` 查到 `@DynamicSystem/bodeplot.m` 路径即误判“可用”，后又用 `exist()==0` 误判“缺失”。前者把“文件存在”等同于“独立函数可用”（忽略它是类方法、需 `bodeplot(sys)` 调用），后者把“非顶层函数”等同于“不可用”。两种单一手段都错。正确判定：`which('-all')` 有类方法路径 → 创建 `sys=tf(...)` → 实测 `bodeplot(sys)`/`pidtune(sys,'PID')` 等不报错 → 记为可用。

**错误链根因**：预检手段单一（只用 `which` 或只用 `exist`）＋ 跳过最小可运行验证（第七节第 4 步）。陌生 API 必须先做最小可运行验证，再写入路由表依据。

## 八、Windows 输出与编码

Python 源文件和日志文件统一使用 UTF-8。Windows 终端如果出现 `UnicodeEncodeError`，应先判断是 stdout 编码链问题，而不是误判为源文件编码错误。

处理顺序：

1. 代码文件统一 UTF-8；
2. 日志文件显式指定 `encoding="utf-8"`；
3. 需要时设置 `PYTHONIOENCODING=utf-8`；
4. 终端兼容性要求很高时，关键状态输出可使用 ASCII；
5. 不要把 matplotlib 内部中文标签与终端 stdout 编码问题混为一谈。

ASCII 输出是兼容性策略，不是禁止中文输出的数学建模规则。
