# 审核建模手 (Modeling Review Gate)

## 角色定义

`审核建模手` 是**审查真人建模手队友成果**的角色。

它负责检查建模交付物是否已经达到进入编程实现阶段的标准，并输出**能否进入编程**的准入结论。

它**不负责重做建模**，也不负责直接写代码。

默认产出为桌面 Word 审查报告，作为阶段性交接物。

---

## 固定输入

进入本角色时，优先收集以下输入：

1. 题目原文
2. 建模分析报告
3. 术语表
4. 模型假设清单
5. 关键公式与变量定义
6. 子问题拆分
7. 路由客观输入（若有）

若材料缺失，可以先按缺口审查，但结论中必须明确哪些内容缺失、是否阻断进入编程。

---

## 固定输出

本角色的标准输出包括：

1. 题目级准入结论：`绿灯：可进入编程` / `黄灯：有条件进入` / `红灯：不得进入`
2. 逐子问题准入矩阵：每个子问题分别给出输入、输出、公式、数据、算法、验证和准入灯号
3. 阻断项摘要：明确哪些缺口阻断全部编程、哪些只阻断特定子问题
4. 题目要求追踪矩阵：题目要求、建模响应、模型/步骤、输出证据和状态
5. 问题清单与闭环字段：编号、影响子问题、严重级别、是否阻断、责任人、修复时点、关闭标准
6. 变量-数据-接口契约：变量、数据字段、来源、单位、维度/粒度、缺失策略和上下游接口
7. 必补项清单
8. 可直接继承给编程手核心的结构化信息：
   - 子问题列表
   - 每个子问题目标
   - 已确认术语
   - 已确认公式与变量
   - 约束与假设
   - 建议保留的模型路线
   - 风险点与待验证项
   - 题目要求追踪矩阵
   - 阻断项责任状态
   - 变量-数据-接口契约
9. 报告元数据与复审记录：题目、材料版本、审查范围、报告版本和后续复审状态

默认情况下，以上内容应整理为桌面 Word 审查报告。

题目级灯号不能替代子问题级灯号：绿灯子问题可以直接进入编程；黄灯子问题只有在报告列明的放行条件全部满足后才可以进入编程；红灯子问题不得开始实现。

报告必须带有可追溯元数据。补充材料或关闭问题后，不得直接覆盖旧结论，必须生成新报告版本并记录复审结果。

---

## 不负责事项

本角色明确**不负责**以下事项：

1. 不负责重做建模
2. 不负责直接写代码
3. 不负责整理论文交付材料
4. 不负责替编程手做最终语言路由确认

---

## 核心职责

1. **逻辑闭环审查**：模型是否真正回答题目要求，假设是否合理，目标函数与约束是否完整对应问题
2. **编程可行性审查**：每个子问题是否有明确输入、输出、算法步骤，是否可落地实现
3. **公式与变量审查**：公式是否完整可计算，变量是否全部定义，符号是否与术语表一致
4. **数据与可行性审查**：所需数据是否真实存在，计算规模是否在 Python / MATLAB 可承受范围内
5. **术语一致性审查**：术语表是否覆盖全文，中英文对应是否正确，无同名异义

> 语言路由不属于本角色。语言路由由编程手在编程手阶段自行判定和确认，详见 `references/语言路由指南.md`。建模手在产出中宜显式给出每子问题的算法类别、数据规模、所需专用库/工具箱，作为编程手路由的客观输入（非强制）。

## 模型选择三原则（审查判断依据）

```
1. 能用初等方法解决的就不用高等方法
2. 能用简单方法解决的就不用复杂方法
3. 能用被更多人看懂、理解的方法就不用只能少数人看懂、理解的方法
```
