本文件供 **审核建模手** 审查真人建模手队友交付物时遵循。该阶段不重新建模，只对既有分析报告、术语表、公式变量与子问题拆分做准入审查，判断是否可以进入编程实现。

## 审查流程

### 第零步：交付物完整性检查（必须最先执行）

检查建模手是否已提供以下 **内容**，内容缺失才影响进入审查；文件拆分形式不是硬性门槛：

- **题目分析内容**：问题分析、模型选择、算法设计、数据要求和必要的参考依据；正式项目推荐放在 `题目分析.md`
- **术语与符号内容**：中英文术语对照、符号定义；正式项目推荐放在 `术语表格.md`
- **路由客观输入**（宜提供，非强制）：每个子问题的算法类别、数据规模、所需专用库 / 工具箱；未提供时由编程手独立推导

**内容缺失** -> 退回建模手补充，记录缺口；如果题目分析与术语表合并在一个完整交付物中、直接由对话提供，或使用用户指定的文件名，只要内容完整即可进入审查；路由客观输入缺失不强制退回。

### 第一步：题目理解核对

核对分析报告是否覆盖：

| 信息类型 | 审查要点 |
|---------|---------|
| 问题背景 | 背景与场景是否描述准确 |
| 问题类型 | 优化 / 预测 / 评价 / 分类判断是否合理 |
| 数据情况 | 已知 / 待求 / 数据特点是否清晰 |
| 约束条件 | 限制与边界是否完整 |
| 目标要求 | 需解决的具体问题是否明确 |

### 第二步：模型选择审查

**在审查模型选择时，必须核对模型的适用性依据是否可追溯。** 对经典教材模型，教材或标准参考书即可；对常规成熟模型，建议记录出处但不因缺少论文信息直接阻断进入编程；对自定义改进、特殊领域公式或明确声称创新/优越性的模型，应核对论文、公式来源或对比证据。

**防冗余原则（必须审查）**：
- 每个模型是否承载独特且不可替代的分析维度
- 模型之间是否形成互补证据链，而非重复验证同一结论
- 若两模型输出揭示同一层面信息，应判定冗余

#### 模型类型审查

| 问题类型 | 应出现的模型 |
|---------|---------|
| 优化问题 | 线性/整数/非线性规划、多目标规划、动态规划、图论模型 |
| 预测问题 | 时间序列分析、回归分析、灰色预测、神经网络（谨慎使用） |
| 评价问题 | AHP、熵权法、TOPSIS、模糊综合评价 |
| 分类问题 | 聚类分析、判别分析、支持向量机 |

### 第三步：编程可行性审查（替代原语言路由选择）

本步骤 **不做语言路由**（路由由编程手在编程手阶段判定）。此处只审查：

1. 每个子问题是否有明确输入 / 输出 / 算法步骤，可落地实现
2. 路由客观输入是否齐全：算法类别、数据规模、所需专用库 / 工具箱（宜提供、非强制）
3. 若建模手已提供路由客观输入，审查其正确性（算法类别是否匹配、数据规模是否属实、所需库是否必要充分）；若未提供，编程手须独立推导路由，不退回、不凭偏好

> 语言路由始终由编程手客观判定与确认，依据见 `语言路由指南.md` 路由审查与独立推导规范。建模手提供则审查，未提供则编程手独立推导。

### 第四步：算法设计审查

1. **求解思路**：步骤是否完整、可复现
2. **算法流程**：是否有清晰流程或伪代码
3. **评价指标**：模型好坏的评判标准是否定义
4. **参数设置**：关键参数取值范围与调整方法是否给出

### 第五步：术语规范审查

核对术语表是否：

1. 覆盖题目与分析过程中的所有专业术语
2. 统一定义并给出明确中文定义
3. 提供标准英文翻译
4. 统一数学符号使用
5. 与分析报告中的符号完全一致

## 交付物缺口处理规则

审查中发现建模交付物不足时，按以下规则处理：

### 规则一：数据不足

| 场景 | 处理方式 |
|------|---------|
| 题目没给具体数据 | 退回建模手确认是否符号参数建模，标注“需实际数据代入” |
| 数据含大量缺失值 | 审查插补率，>30% 时要求建模手在论文中说明局限性 |
| 数据规模太小（<10 条） | 核对是否选用灰色预测、参数检验等小样本方法 |
| 数据只有宏观总量 | 核对比例分配或假设分布的合理性 |

### 规则二：模型不适用

| 场景 | 处理方式 |
|------|---------|
| 首选模型假设不成立 | 要求建模手记录原因并说明备选方案 |
| 所有标准模型不完全匹配 | 核对是否组合 2-3 个模型分阶段求解 |
| 题目是交叉领域 | 核对是否已拆分为多子问题，各自最匹配模型 |
| 计算资源超出合理范围 | 要求建模手说明精度/简化取舍 |

### 规则三：问题类型不明确

按以下决策树判断建模手分类是否合理：

```
题目描述更偏“找到最佳方案”？                    -> 优化类
题目描述更偏“推测未来趋势”？                    -> 预测类
题目描述更偏“比较多个选项”？                    -> 评价类
题目描述更偏“发现数据中的模式”？                -> 分类/聚类
同时涉及以上多种？                              -> 组合类，拆分子问题
```

### 规则四：不确定性处理

- **数据有噪声**：建模手是否引入鲁棒性考量、灵敏度分析
- **参数不确定**：是否做区间估计而非点估计
- **模型不确定**：是否用多模型交叉验证对比
- **假设有争议**：是否显式列出每个假设并说明违反后果

### 规则五：何时退回建模手

**必须退回补充的情况**：
- 题目有多个理解方向且建模手未说明取舍
- 需要做比“合理假设”更强的约束性假设

**可直接进入编码的情况**：
- 缺失输入可由已有数据推导，且建模手已记录推导
- 通用参数默认值（如交叉概率 0.8、显著性水平 0.05）
- 标准建模流程选择（如先预处理再建模）

> **核心原则**：能做合理假设的不要退回，但所有假设必须已记录在分析文档中。

## 模型选择原则（审查判断依据）

| 原则 | 说明 |
|------|------|
| **高效性** | 优先选择计算速度快、效率高的模型 |
| **准确性** | 确保模型能够准确描述和解决问题 |
| **简洁性** | 在满足要求的前提下，选择相对简单的模型 |
| **创新性** | 作为满足适用性、准确性、简洁性和可验证性后的加分项；不得为了新颖而替换适用的经典模型 |
| **实用性** | 尽量避免使用需要长时间训练的复杂模型 |

**谨慎使用的模型**：神经网络（仅在传统方法效果不佳时）、机器学习模型（优先尝试传统模型）、深度学习模型（仅在处理复杂高维数据时）

## 审查报告结构（单一权威结构）

## 准入灯号与放行规则（单一权威规则）

### 绿灯：可进入编程

- 题目要求已逐条映射到模型响应和预期输出
- 子问题的输入、输出、关键公式、变量定义、算法步骤均可执行
- 核心假设已记录，关键数据缺口不阻断实现
- 至少一种结果验证方式可执行
- 不存在未解决的阻断项

### 黄灯：有条件进入

- 主链路已经可以编码
- 仅存在非阻断的参数、展示、补充验证或可延后资料缺口
- 必须在报告中写明条件、责任人、补充时点和关闭标准
- 绿灯子问题可以直接进入编程
- 黄灯子问题只有在报告列明的放行条件全部满足后，才可以进入编程
- 红灯子问题不得开始实现

### 红灯：不得进入编程

- 题意或多个解释方向未决
- 目标函数、约束、关键公式或关键变量无法计算
- 关键数据不可获得且没有替代方案
- 模型与问题类型明显不匹配
- 没有任何可执行的结果验证路径

题目级结论用于说明整体边界，子问题级结论用于实际放行。题目总体为黄灯时，不得因此暂停已经为绿灯的子问题；题目总体为绿灯时，也不得绕过仍为红灯的子问题。

## 生成审查报告（Word）

**触发**：用户明确要求出报告，且审查已完成。
**工具**：调用 `tools/docx` 技能（python-docx）生成文档。
**保存路径**：`C:\Users\qingf\Desktop\建模审查报告_YYYYMMDD_HHMM.docx`
**中间物规则**：该文件为阶段性交接材料，不回写项目目录，不参与 git。
**内容**：按上方「审查报告结构」填充（元数据、准入矩阵、题目要求追踪、问题闭环、变量-数据-接口契约、验证矩阵、复审记录和可复制修改稿）。
**步骤**：
1. 汇总本次审查结果（元数据 / 结论 / 准入矩阵 / 交接契约 / 问题清单 / 验证矩阵 / 复审记录 / 路由待确认事项）
2. 调用 `tools/docx` 生成 `.docx`，保存到桌面路径
3. 向用户回执文件完整路径
