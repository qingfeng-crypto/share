# 语言路由指南 (Language Routing Guide)

> 本文件为路由规范唯一权威来源，SKILL.md 中路由相关规则均引用本文件。

本文件供 `审核建模手` 了解编程手后续如何做方法-语言路由，以便在审查阶段只核对建模手提供的**路由客观输入**是否可信。最终路由结论始终由编程手在编程手阶段独立判定与确认。

作为编程手，在代码实现前对每个子问题判定推荐使用的**解题方法**和**编程语言**，自行建立“**方法-语言路由表**”并向用户确认后执行。推荐必须基于题目与算法的客观条件，不得由 AI 的语言偏好或当前工具可用性决定。建模手在交付物中宜提供（非强制）每子问题的算法类别、数据规模与所需专用库/工具箱，作为路由的客观输入；未提供时由编程手独立推导。

---

## 前置原则：求解器优先于语言

> **优化求解阶段，选语言之前先选求解器。** 路由决策的起点是问题类型和求解器能力，不是语言偏好或工具熟悉度。

### 三个强制检查问题

在优化求解阶段建立路由表之前，必须先回答：

1. **这是什么问题类型？**（连续 LP / 整数规划 / MILP / 非线性规划 / 微分方程 / 蒙特卡洛 / ...）
2. **各候选语言在这个类型上有什么求解器？**（原生内置 / 第三方；商用级 / 学术级；一行 API / 需手写框架）
3. **类型匹配度是否一票否决？**（若一方有商用求解器而另一方无，直接出局，不继续比较）

### 求解器事实核验合同

对优化题以及 NLP、MINLP、MILP、QP、ODE/PDE、控制系统、信号处理或需要最优性/可行性证明的子问题，路由表必须逐候选记录：

| 核验项 | 必填内容 |
|---|---|
| 求解器名称与版本 | Python/MATLAB 候选求解器、库或工具箱及版本 |
| 目标函数支持 | 是否原生支持当前目标函数形式，若不支持如何处理 |
| 约束支持 | 是否原生支持全部等式、不等式、非线性、逻辑或边界约束 |
| 变量类型支持 | 连续、整数、0-1、边界和其他变量类型是否覆盖 |
| 最优性/可行性/误差能力 | 能否提供题目所需证明、状态或误差边界 |
| 核验来源 | 官方文档、版本文档或最小可运行示例；不得写“应该支持” |

高风险问题缺少核验来源时，不得进入用户确认和编码。普通数据处理或绘图任务也必须记录候选库及版本，确认其覆盖实际调用能力。

### 路由表前置硬约束扫描

在给出推荐语言前，必须用一句话写出当前问题类型的求解器硬约束，并逐一检查候选求解器是否满足。无法回答“这个问题最少需要什么求解器能力”时，路由表不得继续，必须先回到题目和模型定义。

| 检查项 | 必填内容 |
|---|---|
| 问题类型 | LP / IP / MILP / NLP / ODE/PDE / 仿真 / 其他明确类型 |
| 求解器硬约束 | 例如：含非线性约束，必须使用支持非线性约束的 NLP 求解器；不得用 LP/IP 求解器替代 |
| Python 候选求解器 | 名称、是否匹配、不能满足时的具体原因 |
| MATLAB 候选求解器 | 名称、是否匹配、不能满足时的具体原因 |
| 一票否决 | 哪个候选因能力缺失直接排除，或明确“无一票否决”及理由 |

### 实践案例：整数规划的选型教训

**场景**：求解 `max z = x1 + x2` 的整数规划问题，约束含分数系数，最终答案 `x1=3, x2=1, z=4`。

**错误选型**：Python + scipy。scipy 只有 `linprog`（连续 LP 求解器），没有内置整数规划求解器。结果被迫手动编写循环调 LP 模拟分枝定界，效率低且容易出错。

**正确选型**：MATLAB + `intlinprog`。`intlinprog` 是内置商用级 branch-and-cut 求解器，底层 C/C++ 编译，支持 presolve、割平面、启发式搜索，一行调用直接出最优解。

**错误决策链**：“Python 方便我手动编码分枝定界（教学演示思维）” -> 忽视了求解器能力差距。

**正确决策链**：“整数规划 -> 需要 MILP 求解器 -> Python scipy 无内置整数规划求解器 -> MATLAB `intlinprog` 一票通过”。

### 一句话总结

> 优化求解选型：不要问“用什么语言写代码”，先问“这个子问题用什么求解器解”。求解器能力决定语言，不是反过来。

## 一、最高优先级原则

Python 和 MATLAB 是并列候选语言。语言推荐必须依次考察：

1. 模型和算法的原生适配度；
2. 数据规模、矩阵稀疏性、数值稳定性和性能要求；
3. 可用工具箱与库的实际能力；
4. 上下游数据接口和整体流程一致性；
5. 代码可解释性、复现性和竞赛交付成本。

以下因素不得作为偏向 Python 的理由：AI 更熟悉 Python、Python 示例更多、当前技能对 Python 支持更多、Python 环境已先检查、MATLAB MCP 尚未检查或 MATLAB MCP 是否可用。Python 与 MATLAB 必须在路由前以对称方式记录候选能力和环境状态；环境状态只影响执行方式，不影响语言路由。正常情况下 MATLAB 任务通过 MCP 以“先写 `.m` 文件再 `run_matlab_file`”方式执行；仅当 MCP 不可用或会话无法启动时，才生成 `.m` 文件供用户手动运行。

### 路由前对称预检规则

在推荐语言前，必须同时记录 Python 和 MATLAB 的候选预检状态：

| 候选 | 必须记录 | 不得做出的推断 |
|---|---|---|
| Python | 解释器版本、候选库及版本、缺失依赖、运行状态 | “Python已检查所以默认推荐” |
| MATLAB | MATLAB版本、MCP连通性、候选工具箱状态、具体错误 | “MATLAB未检查所以不可用” |

预检失败只说明当前执行路径存在阻碍，不说明该语言在模型和求解器层面不适配。正式语言确认后，才根据最终语言执行完整运行时检查；混合语言任务两边都必须检查。

## 二、路由判断原则

> **原则**：先确定“问题类型 -> 求解器能力 -> 候选语言”，再确认语言。
> 求解器能力的差距（有 vs 无、商用级 vs 学术级）构成一票否决，不是“性能更优”的比较。

### 常见绕过手法（违规）

- 把 NLP 重描述为“枚举 + MILP + 后验证”，绕开非线性求解器硬约束
- 在整数规划中绕过整数支持缺失，用连续 LP 或手写循环冒充原问题求解
- 用“规模小”跳过求解器匹配、最优性要求或另一语言的可行性分析
- 静默改写目标函数、约束或变量类型，让某语言看起来可行

这些做法改变了问题结构或削弱了正确性要求，不得作为语言路由依据。若确实要采用近似、分解或枚举，必须单独说明新问题类型、损失的最优性保证和验证方案，并经用户确认。

```
问题类型               Python有什么   推荐    说明
────────────────────────────────────────────────────────────────────────
连续线性规划 (LP)       linprog  ✅    均可    scipy / linprog 均可
整数规划 (IP)            pulp/ortools 可支持（学术级）  ✅   均可    学术场景可用；工业级仍推荐 MATLAB
混合整数规划 (MILP)      pulp/ortools 可支持（学术级）  ✅   均可    同上
非线性规划 (NLP)        optimize ✅   均可    复杂问题选 MATLAB
微分方程 (ODE/PDE)      不全    ⚠️    MATLAB  ode45/pdepe 更完整
矩阵运算 / 线性代数      numpy   ✅    均可    小规模 Python 即可
信号处理 / 控制系统     无内置   ❌    MATLAB  DSP/Control Toolbox
蒙特卡洛仿真            random  ✅    均可    复杂仿真选 MATLAB
数据预处理 / EDA        pandas  ✅    Python  无可替代
统计推断 / 假设检验     scipy   ✅    Python  scipy.stats
机器学习 / 深度学习     sklearn ✅    Python  PyTorch
可视化 (Python首选)      mpl/seaborn ✅ Python  Python 首选，MATLAB 合规例外
文档 (PDF/Excel/Word)   openpyxl ✅   Python  技能内建 tools
图论与网络分析          networkx ✅   Python  轻量
模糊综合评价 / AHP      可自定义 ✅   均可    Python 可读性更好
灰色预测 / 时间序列     statsmodels ✅ 均可  数据量大选 MATLAB
```

**使用流程**：遇到题目 -> 在上表找到问题类型 -> 看“推荐”列和“说明”列 -> 确认决策依据。

> **出图规则：Python 首选，MATLAB 合规例外**：即使子问题的计算在 MATLAB 完成，论文正式图表通常仍优先将结果导出（`.csv` / `.mat` / `.xlsx`）后由 Python 读取绘图，以保证风格统一和交付稳定。仅当图高度依赖 MATLAB 专用工具箱可视化，或 MATLAB 已能以不高于 Python 重绘的成本达到同等视觉质量与交付标准时，才允许直接在 MATLAB 出图；此时须严格遵守可视化规范中的“MATLAB 视觉样式规范”与“MATLAB 文本与公式渲染规范”。

## 三、分步执行规划格式

在 `题目分析.md` 的语言路由章节，按以下格式填写：

```markdown
### 4.2 分步执行计划

| 步骤 | 操作描述 | 推荐方法 | 推荐语言 | 理由 |
|------|---------|---------|---------|------|
| 1 | 数据读取与清洗 | 数据预处理 | Python | pandas 高效 |
| 2 | 线性规划求解 | 线性规划 -> intlinprog | MATLAB | 整数规划 intlinprog 更快 |
| 3 | 结果可视化 | 可视化 | Python | matplotlib 生态 |
```

## 四、用户确认闸门

编写或执行每个子问题前，必须使用**一题一张 Markdown 表格**展示，不把多个子问题压缩到一张超宽表中：

| 项目 | 推荐内容 |
|---|---|
| 子问题 | [子问题名称] |
| 前序衔接与继承内容 | [总报告/术语表/前序子问题结论/共享变量/输入输出接口；首题填写“无前序产出，但继承总报告”] |
| 问题类型 | [模型/算法类型] |
| 硬约束扫描 | [该问题类型必须满足的求解器能力 + 两种候选的匹配情况] |
| 候选求解器匹配度 | [Python候选：匹配/不匹配及原因；MATLAB候选：匹配/不匹配及原因] |
| 求解器事实核验 | [名称/版本；目标函数支持；约束支持；变量类型支持；最优性/可行性/误差能力；核验来源] |
| 推荐方法 | [模型/算法类型] -> [具体方法]（[适用库或工具箱]） |
| 推荐语言 | [Python / MATLAB] |
| 客观依据 | 至少两条，来自模型、算法、数据规模、数值稳定性、性能、工具能力或上下游接口 |
| 另一语言 | [可行/不适合]；说明具体可行性与不优先原因 |
| 反推验证 | [换用另一语言是否仍保持原问题类型、约束和验证要求；不优先的具体技术原因] |
| 执行方式 | [Python / MATLAB MCP / MATLAB 手动降级] |
| 输出与下一步 | [文件、格式和依赖] |

表格后必须保留：

> 请确认：**A 按推荐执行；B 改用另一语言；C 比较两种实现；D 暂缓。**

用户确认前不得写代码、运行代码、调用 MCP 或自动进入下一个子问题。用户改选后，必须在路由表中记录最终选择及用户理由。

### 路由完成后的反推验证

推荐语言填写完成后，必须反向假设改用另一语言，并回答：

1. 是否仍能使用与原问题类型匹配的求解器；
2. 是否会改变目标函数、约束、变量类型或最优性要求；
3. 是否仍能执行同等强度的验证；
4. 若另一语言可行但不优先，具体技术原因是什么（求解器能力、工具箱、数值稳定性、性能、接口或交付成本），不得写“习惯”“偏好”“更熟悉”。

若反推发现推荐语言实际上无法满足原模型约束，必须退回重做路由，不得用“枚举+后验证”“改写成线性近似”等方式静默改变问题类型。

### 逐题确认不是孤立分析

- 每个子问题虽然必须单独确认，但确认时必须继承建模手总报告、术语表、总体模型主线、共享假设、前序子问题结论、数据结构、文件接口和已确认路由。
- 本指南中的“独立推导”仅表示编程手对当前子问题的推荐方法和语言进行客观核验，不表示脱离前序建模成果重新开始。
- 若当前题目、建模手交付物与前序结果冲突，必须先报告冲突并回溯修订，不得为了局部运行而静默改变符号、假设、输入输出或模型。
- 每个子问题完成后，必须记录实际方法、语言、输入、输出、关键假设、验证结果及对后续子问题的影响。

## 五、执行方式说明

| 语言 | 执行方式 | 降级方案 |
|------|---------|---------|
| Python | 直接 `python 文件名.py` 执行 | N/A |
| MATLAB | 先将代码写入 `.m` 文件，再通过 MCP 调用 `run_matlab_file` 执行；自动会话模式可连接已运行 MATLAB 或启动新会话 | MCP 不可用、会话无法启动或用户要求手动运行时，提示用户在 MATLAB 中直接运行生成的 `.m` 文件 |

### MATLAB 执行硬性规则（避免内联执行报错）

MATLAB 的内联执行路径（把代码作为字符串直接 `eval` / 命令行执行）**不支持顶层 `function` 定义、也不支持中文字符**，会报“函数定义在此上下文中不受支持”“文本字符无效”。因此必须遵守：

- **一律先写 `.m` 文件，再用 `run_matlab_file` 执行**，禁止内联执行含函数定义或中文的求解代码；
- **文件名必须纯 ASCII**（英文/数字/下划线，如 `machine_tool_lp.m`），禁止中文文件名；
- 代码体内可含中文注释/字符串（UTF-8 的 `.m` 文件 MATLAB 能正常读取），但不要把整段逻辑塞进单条命令字符串；
- `evaluate_matlab_code` 仅可用于轻量连通性检查，**不可用于执行实际求解代码**；
- 若 `run_matlab_file` 仍报中文/函数相关错误，先核对文件名是否为 ASCII、代码是否写在文件内而非内联。
- 拿不准 MATLAB 语法、选项名或版本行为时，**查官方文档与 `MATLAB 避坑指南.md`（见该文件顶部链接）**，不要凭记忆猜；本机 MATLAB 版本基线为 R2024b，该指南所有写法均按 R2024b 可用能力给出。

## 六、冲突解决规则

当某子问题两种语言均可时，按以下优先级选择：

1. **子任务整体一致性**：若子问题内的多个步骤语言不一致，重新评估是否需要拆分子问题
2. **后续任务依赖**：优先保持上下游语言一致，减少数据格式转换
3. **性能优先**：计算密集且 MATLAB 明显更快的，选择 MATLAB
4. **生态优先**：数据处理、可视化、文档生成优先 Python

## 七、路由审查与独立推导规范

语言路由始终由编程手客观判定，不盲从建模手，也不因缺输入退回或凭偏好。

- **情形一（建模手已提供路由客观输入）**：逐项审查算法类别是否真匹配该子问、数据规模是否属实、所需库/工具箱是否必要且充分；发现错误/不当须纠正并给出依据，不盲从。
- **情形二（建模手未提供路由客观输入）**：不得退回了事，也不得凭偏好猜；回到题目与每个子问，独立分析所需技巧（算法类别、数据规模、数值稳定性、生态工具、上下游接口），依本指南客观推导 Python/MATLAB，并给出至少两条客观理由，照常走用户确认闸门。

> 本规范被审核建模手审查报告“路由客观输入确认”环节引用：报告须呈现“建模手是否提供 + 编程手审查结论 + 编程手独立推导推荐方法及语言、客观依据”。

## 八、两条常见表述禁令（基于实测反馈）

### 禁令一：禁止用“语言统一”作为路由借口

“全题统一语言”“与题 X 保持一致”**不得**作为单题推荐语言的独立依据。每个子问题必须按其自身的求解器硬约束、生态匹配和上下游接口独立路由。

- 若真要语言统一，应让**所有**相关子问题都改走同一语言（用户明确选择 C 模式），而不是让某一题在客观不匹配时“跟着”另一题走。
- 审查时若发现“题一已路由 MATLAB、题三却以与题一一致为由推 Python”这类自相矛盾的论述，直接判路由依据无效，要求重写客观依据。
- **“已安装 / 零依赖 / 环境已就绪”不得作为单边推 Python 的决定性依据**：当某题客观上“均可”（两边求解器对称）或 MATLAB 本就更优（如复杂仿真、灵敏度分析、信号处理）时，“Python 已安装零依赖”只能作为并列便利项，不得据此把结论单边压向 Python。这是第八条明文禁止的偏置来源之一（同禁令一列举的“Python 环境已先检查”）。若路由表依据中出现“scipy 已安装所以选 Python”而另一语言实际能力对等或更强，直接判依据无效。

### 禁令三：“均可”题必须显式标注并据规则裁决

当某子问题 Python 与 MATLAB 求解器能力对称（均为“均可”）时：

- 推荐语言栏**必须显式写“均可”**，不得写成单边“推荐 X”又自认“偏好”——否则会与真正单边题（如 MATLAB 独有 `pidtune`、Python 独有 `scipy.stats.bootstrap`）表述无法区分，掩盖真实能力差距。
- “均可”题的倾向方（若给出）必须依据第六节冲突解决规则的优先级裁决：① 子任务整体一致性 → ② 后续任务依赖 → ③ 性能优先 → ④ 生态优先；并写明对应客观理由，不得退回“偏好”“便利”等空泛词。
- 审查时若发现两道对称“均可”题落点漂移（一道落 MATLAB、一道落 Python，依据都写“偏好”），直接判表述不一致，要求统一按上述规则重写。
- **“均可”题的倾向方必须限定生效场景**：若倾向某语言只在特定子场景成立（如 50 城扩展用启发式、主场景 15 城精确解两侧对称），须显式声明“主场景仍纯均可，倾向仅在 X 场景下成立”，不得让读者误判主场景偏置。
- **性能/复杂度数字须有依据**：路由表出现的运行时间、复杂度、规模阈值等具体数值，必须标注来源或明确“估算”，不得凭印象写无出处的具体数字（如“全量 SVD 约 2000 秒”这类无来源断言）。性能数字同属事实核验范围，违反“不得写应该支持”原则。
- **出图分工须与“MATLAB 合规例外”条件一致**：若子问题计算在 MATLAB 且图高度依赖其专用工具箱可视化（如 `pdeplot`），默认应在 MATLAB 直接出图，不得默认导出甩给 Python；仅当图是普通图表、Python 重绘成本更低，或用户明确要求统一绘图风格时，才导出后由 Python 绘图。计算语言与绘图语言可以不同，但“MATLAB 算、Python 画”不能一刀切，须逐题依据出图规则判定。
- **“均可”题不得互相引用倾向形成循环**：若题 X 倾向题 Y、题 Y 又倾向题 X（如 ⓒ 因 ⓓ 倾向 Python、ⓓ 又因 ⓒ 倾向 Python），至少一题须回落为纯“均可”，或显式声明“仅当用户选择题组整体对齐为某语言时才生效”。不得用另一个同为“倾向”的题支撑本体的倾向结论。

### 禁令二：可视化中文渲染必须显式核验，不得默认通过

任何用 matplotlib / MATLAB 出图、且国赛交付需中文标注（图例、坐标轴、标题、标注）的子问题，其硬约束扫描不得把“中文字体正常渲染”写成已实现的目标；必须将其列为**显式待核验项**进入执行清单：

- Python：须显式设置 `plt.rcParams['font.sans-serif']`（如 `SimHei` / `Microsoft YaHei`）并验证无方框乱码；
- MATLAB：须确认字体配置或导出后中文标注方案；
- 未列入核验清单即视为高风险缺口，不得标绿灯。
> 与逐子问确认闸门的关系：审查报告第四节给出的**方法-语言路由**是审查阶段的汇总推荐，不取代编程手阶段既有的逐子问 B 模式确认闸门。编码前仍须对每个子问题再次展示**推荐方法**、**推荐语言**、>=2 条客观理由、另一语言可行性与不优先原因，并等用户确认。
