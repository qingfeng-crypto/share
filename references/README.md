# 数学建模三轨并行工作指南

> 注：本技能由**一个 AI 助手**承载三轨角色，不表示三个独立 AI。

本文档介绍数学建模技能中三轨的职责、工作流程和协作关系。

---

## 集成的子Skill

本技能集成了四个专业的文档处理子Skill，位于 `tools/` 目录下：

- **`tools/docx`** - Word文档处理
  - 创建、读取、编辑 .docx 文件
  - 生成格式规范的数学建模论文
  - 支持表格、图片、公式等复杂格式

- **`tools/pdf`** - PDF文档处理
  - 读取PDF格式的题目文档
  - 提取文本和表格数据
  - 支持PDF合并、拆分等操作

- **`tools/xlsx`** - Excel表格处理
  - 读取和编辑 .xlsx 文件
  - 处理题目附带的数据表格
  - 指定 Excel 模板时保留结构和公式

- **`tools/paper_search`** - 论文搜索
  - 通过OpenAlex API搜索学术论文
  - 为数学建模论文提供参考文献支持
  - 自动生成标准引用格式
  - 支持摘要重建和多字段搜索

**注意：原 `scripts/` 目录下的Python脚本已被集成到 xlsx skill 中，现在使用 xlsx skill 替代原有的表格处理功能。**

## 72 小时时间线（参考）

国赛标准赛程约 72 小时，推荐并行时间线如下：

| 时段 | 主责 | 并行窗口 |
|------|------|----------|
| T0-T4 | 建模手读题、子问题拆解、框架搭建；编程手启动数据清洗与字段/单位约定；论文手搭论文框架 | 三轨并行 |
| T4-T12 | 建模手逐子问题产出分析报告（每产出一个子问题即可移交审查与编码）；编程手每接一个子问题开始一个并行窗口；论文手撰写已可写章节 | 子问题级并行 |
| T12-T36 | 各题计算稳定，编程手集中补验证与图表；建模手若有余力协助查论文手逻辑；论文手主体撰写与图表整理 | 计算→论文并行 |
| T36-T72 | 论文手成稿、精修、排版；建模手/编程手配合补缺补漏 | 前端→后端并行 |

> **并行协作说明**：国赛真实协作中三人通常**同时读题、并行推进**，并非严格瀑布。典型并行窗口：
> - **建模手分析期间**：编程手可启动数据预处理，产出干净数据表与字段/单位约定，供建模与实现共用。
> - **第一题计算启动后**：论文手可同步搭建论文框架，并开始撰写已明确的部分。
> - **子问题之间**：前序子问题结果稳定后，后续子问题的建模与编程即可启动，无需等待全题建模完成。
> - **多题之间**：第二题建模期间，第一题正文撰写与结果可视化可并行；第三题建模与第二题计算可并行。

### 三轨并行概览

| 轨道 | 定位 | 核心职责 | 主要输出 |
|:----:|:----:|---------|---------|
| **建模分析（含子问题审查）** | 建模阶段 | 逐子问题产出分析报告、术语表；每产出一个子问题即同步进行子问题级审查，不设独立审查阶段 | 子问题分析报告、术语表、审查结论 |
| **编程手核心** | 实现阶段 | 基于建模手产出（或部分产出）完成路由、代码实现、结果验证和图表产出；支持在建模分析未完成时先行编码 | 代码、结果文件、图表、README |
| **交付论文手** | 交付阶段 | 将实现结果整理为论文协作可直接接收的材料包；支持在全部计算完成前早期介入搭框架 | 交付清单、材料包、论文协作用说明 |

### 并行窗口与交接契约的关系

并行窗口是**行为规则**，交接契约是**载体**。每次子问题产出后，通过交接契约触发下游接收；下游收到后即可启动对应子问题的编码/撰写，形成并行窗口。并行窗口不独立于交接契约存在，交接契约是并行协作的唯一触发方式。

旧 `建模手/`、`编程手/` 目录仍保留，作为过渡参考与兼容备份；主说明层默认不再将其作为首选入口。

## 建模分析（含子问题审查）

建模分析阶段负责产出分析报告、术语表和子问题拆解；每产出一个子问题即同步进行子问题级审查，不设独立审查入口。

### 角色介绍

- **建模手**：逐子问题产出分析报告与术语表；每完成一个子问题即触发同步审查。
- **审查节点**：随建模产出同步进行，逐子问题审查，不等待全题建模完成。
- **下一阶段接收方**：编程手核心基于建模手产出物继续实现，无需等待审查放行。

**工作输入**：题目文件 + 前置材料
**工作输出**：子问题分析报告 + 术语表 + 审查结论（随每个子问题产出）

### 核心职责（建模分析维度）

| 维度 | 审查内容 |
|------|---------|
| **逻辑闭环** | 模型是否真正回答题目要求，假设是否合理，目标函数与约束是否完整对应问题 |
| **编程可行性** | 每个子问题是否有明确输入、输出、算法步骤，是否可落地实现 |
| **公式与变量** | 公式是否完整可计算，变量是否全部定义，符号是否与术语表一致 |
| **数据与可行性** | 所需数据是否真实存在，计算规模是否在 Python / MATLAB 可承受范围内 |
| **术语一致性** | 术语表是否覆盖全文，中英文对应是否正确，无同名异义 |

### 审查工作流程

> 审查随建模产出同步进行，不设独立审查阶段；具体审查细则以 `roles/审核建模手/SKILL.md` 为准。该阶段**可跳过审查结论**，不强制作为进入编程的前置闸门；编程手可在建模手产出部分分析后先行启动编码。

```
第一步：子问题产出
    ↓
    建模手每产出一个子问题的分析报告，即可触发同步审查

第二步：子问题级五维度审查
    ↓
    检查逻辑闭环、编程可行性、公式变量、数据可行性、术语一致性

第三步：形成三色准入结论（逐子问题）
    ↓
    输出绿灯可进入编程 / 黄灯有条件进入 / 红灯不得进入的明确判断
    逐子问题标记输入、输出、公式、数据、算法、验证和放行条件
    报告记录元数据、验证矩阵和复审版本，不静默覆盖历史结论

第四步：移交实现阶段（可选）
    ↓
    若队友选择先经过审查，则将审查通过材料交给编程手核心继续实现；
    若队友选择跳过审查，编程手核心可直接基于建模手产出物开始实现。
```

### 问题类型与模型匹配

| 问题类型 | 典型特征 | 推荐模型 | 算法文档 |
|---------|---------|---------|---------|
| **优化问题** | 资源分配、路径规划 | 线性规划、整数规划、图论 | 01-优化算法 |
| **预测问题** | 时间序列、趋势预测 | 灰色预测、ARIMA、LSTM | 02-预测类算法 |
| **评价问题** | 方案选优、绩效考核 | AHP、TOPSIS、熵权法 | 03-评价类算法 |
| **分类问题** | 数据聚类、模式识别 | K-Means、DBSCAN、SOM、GMM | 05-统计分析 |
| **仿真问题** | 系统模拟、风险分析 | 蒙特卡洛、元胞自动机 | 06-综合类算法 |

### 子问题级审查节点规范

- **触发时机**：建模手每产出**一个子问题**的分析报告，即可立即启动该子问题的审查，不等待全题建模完成。
- **审查维度**：逻辑闭环、编程可行性、公式与变量、数据与可行性、术语一致性。
- **三色准入**：绿灯可进入编程 / 黄灯有条件进入 / 红灯不得进入。
- **产物格式**：逐子问题标记输入、输出、公式、数据、算法、验证和放行条件。
- **版本管理**：报告记录元数据、验证矩阵和复审版本，不静默覆盖历史结论。
- **可跳过**：审查结论仅为参考，不强制作为进入编程的前置闸门；编程手可在建模手产出部分分析后先行启动编码。

### 交接契约规范

交接契约是阶段间或子问题间传递的**结构化产物**，保证信息不丢失、不歧义：

- **建模手 → 编程手**：子问题分析报告 + 术语表 + 数据文件（可部分产出）+ 审查结论（可选）。编程手基于此判断可否实现并开展编码。
- **编程手 → 论文手**：代码 + 结果文件 + 图表 + README + 关键口径说明。论文手基于此整理论文协作材料包。
- **审核建模手 → 编程手**：审查结论 + 问题清单（可选）。辅助判断风险点，不强制阻塞编码。

### 审查记录与交接契约的分工

- **子问题审查记录**：由审核建模手产出，是**上游质量检查**记录，包含审查维度结论、灯号、放行条件、已知风险。编程手/论文手须核对，但不对下游产生强制约束。
- **交接契约**：由交接双方（建模手→编程手、编程手→论文手）共同签收，是**上下游交接清单**，包含产出清单、接收核对项、关键假设、变量定义、数据格式、接口约定。下游须逐项核对后签收，签收后方可启动下一轨工作。
- **分工原则**：审查记录解决"质量是否合格"的问题，交接契约解决"交付是否完整"的问题。两者配套使用，不互相替代。

## 第二阶段：编程手核心

编程手核心负责将已审查通过的建模成果转化为可运行代码，并完成验证、结果输出和图表产出。

### 角色介绍

编程手核心阶段负责将建模方案转化为可执行的代码，产出计算结果和可视化图表。

**工作输入**：题目文件 + 建模分析文档（或部分产出，不强制要求审查通过）；若建模分析尚未完全完成，可先对已明确子问题启动编码
**工作输出**：代码文件 + 结果文件 + 可视化图表 + README.md

### 核心原则（必须严格遵守）

**⚠️ 编程语言确认（第一条，必须最先执行）**：
- **在编写任何代码之前，必须先向用户确认使用的编程语言**
- 如果用户未指定，必须按每个子问题的客观条件比较 Python 与 MATLAB，给出推荐及理由后等待用户选择
- **禁止**在未确认编程语言的情况下直接开始编写代码

**遵循你的建模分析文档**：
- **严格按照分析思路**：必须完全按照你在建模分析阶段写出的分析文档中的思路进行代码编写
- **严格使用指定的模型和算法**：必须使用你选择的数学模型和算法，不得自行更换
- **保持一致性**：代码实现应与你的建模分析文档保持完全一致

**超时处理原则**：
- 当代码运行超时时，**加长等待时间**，不要重新写简化的代码

### 核心职责

| 职责 | 具体内容 |
|------|---------|
| **代码编写** | 根据建模文档编写完整可运行的代码 |
| **语言支持** | Python / MATLAB |
| **结果输出** | 确保结果正确输出到文件和终端 |
| **数据可视化** | 生成符合 SCI/Nature 风格的精美图表 |
| **文档说明** | 撰写 README.md 项目说明文档 |

### 工作流程

```
第一步：理解需求
    ↓
    读取：建模分析文档
    路由：逐个子问题客观比较 Python / MATLAB
    确认：等待用户确认后再编码
    理解：题目要求和建模方案

第二步：代码设计
    ↓
    划分：功能模块
    设计：数据结构
    确定：算法实现方法
    规划：可视化图表

第三步：代码实现
    ↓
    编写：结构清晰的代码
    添加：必要的注释
    运行：测试确保正确

第四步：结果验证
    ↓
    确保：结果正确输出
    判断：结果正确性（结合题目、建模文档、运行效果）
    如不正确：进入迭代改进

第五步：迭代改进
    ↓
    如结果不正确：改进代码
    重新运行：验证改进效果
    循环：直到结果正确

第六步：结果输出与可视化
    ↓
    输出：终端打印关键结果
    保存：CSV 文件（不使用 TXT 作为结果总结）
    生成：可视化图表（集成式、3D增强）

第七步：文档撰写
    ↓
    产出：README.md 说明文档
```

### 可视化代码编写原则

**集成式可视化**：
- 可视化代码应与解决问题的主代码一起编写
- 嵌入在数据处理的合适位置
- 运行时可以实时获取数据和画图
- 而不是在运行完成后再单独画图

**3D图表使用**：
- 在合适的场景下使用3D图表以增强视觉效果
- 适用场景：多维数据展示、优化过程可视化、聚类结果展示等

### 可视化约束（重要）

```
┌─────────────────────────────────────────────────┐
```

## 第三轨：交付论文手

交付论文手阶段负责把编程阶段已经产出的代码、结果、图表和说明材料整理为论文协作者可直接接收的材料包。该阶段**可早期介入**，不强制等待全部计算完成。

### 角色介绍

- **交付论文手**：按论文协作需要整理结果、图表、口径说明、文件清单和交付约束；可在代码与图表稳定后或全部计算完成前启动，先搭论文框架和撰写已出结果的章节。

**工作输入**：代码、结果文件、图表、README、必要的术语和审查结论（部分可用）
**工作输出**：材料包 + 交付说明 + 面向论文协作的结构化清单

### 典型交付内容

```
第一步：收集实现产物
    ↓
    汇总代码、结果表、图表、关键参数说明

第二步：整理论文协作材料
    ↓
    对齐命名、口径、图表说明、结果出处

第三步：输出可交付材料包
    ↓
    供论文手或写作协作者直接接收和使用
```

## 阶段协作

### 信息传递链

```
建模手 ──→ 交接契约 ──→ 编程手 ──→ 交接契约 ──→ 论文手
  │            │           │            │           │
  │ 子问题分析  │ 子问题审查  │ 代码实现    │ 图表结果   │ 论文交付
  │ + 术语表    │ + 问题清单  │ + 结果文件  │ + README   │ 材料包
  │            │           │            │           │
  └────── 并行握手 ─────────── 并行握手 ────────────┘
           不设独立闸门          可早期介入
```

### 关键交接点

| 交接点 | 传递内容 | 接收方使用 |
|--------|---------|-----------|
| 建模手 → 编程手 | 子问题分析报告、术语表、数据文件（可部分产出）+ 审查结论（可选） | 判断可否实现并开展编码；不强制要求先经过审查 |
| 编程手 → 论文手 | 代码、结果、图表、README、关键口径说明 | 整理论文协作材料包；可早期介入，先搭框架 |
| 审查节点 → 编程手 | 审查结论、问题清单（可选） | 辅助判断风险点，不强制阻塞编码 |

### 协作要点

1. **术语一致性**：前序术语表应贯穿三轨
2. **交接契约优先**：阶段间传递必须基于交接契约，缺项时接收方有权要求补全或用户授权跳过
3. **并行窗口**：编程手可在建模手分析期间启动数据预处理；论文手可在第一题计算启动后早期搭建论文框架
4. **子问题级推进**：前序子问题结果稳定后，后续子问题即可启动，无需等待全题建模完成
5. **交付可复用**：实现阶段产物应便于论文协作者直接接收

## 常见问题

### 建模分析（含子问题审查） FAQ

**Q: 如何选择合适的算法？**
> A: 查看 `assets/README.md` 中的"按题型查找"表格。

**Q: 术语表为什么必须产出？**
> A: 确保三轨术语一致，提高专业性。

**Q: 必须产出哪些文件？**
> A: `题目分析报告.md` 和 `术语表格.md` 两个文件。

### 编程手核心 FAQ

**Q: 用户未指定编程语言怎么办？**
> A: 按每个子问题的模型、算法、数据规模、工具能力和上下游接口客观比较 Python 与 MATLAB，说明推荐理由、另一语言的可行性和执行方式，等待用户确认后再写代码。不得因为 AI 偏好 Python 或 MATLAB MCP 状态而偏置推荐。

**Q: 子图数量如何把握？**
> A: 不硬性封顶。以"核心结论能一眼读懂"为上限：常见单图 / 1×2 / 2×2 / 2×3，敏感度分析等对比可用 3×3 甚至更大网格；堆砌无关面板或冗余面板（遮盖后仍可读出结论）才应拆分删减。

**Q: 表格文件如何处理？**
> A: 题目输入表格只读不写；普通结果汇总用 CSV；指定 Excel 模板保持结构不变，只填写数据。
